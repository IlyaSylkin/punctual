# Замеры фидов

Разведочные замеры, на которых основаны решения по архитектуре и контракту.
Скрипты: [tools/probe/](../tools/probe/).

**Это не результаты проекта.** Всё измерено на **Хельсинки** в окне
**3.5 часа** 14.09.2026. Такого окна хватает, чтобы принять решения по схеме
хранения и контракту, но не хватает, чтобы утверждать что-либо о точности
прогнозов: она меняется по часам, дням и сезонам. Результаты проекта считаются
на накопленной истории и публикуются отдельно.

---

## 1. Состав фидов

Доля записей, где поле присутствует. Считается `tools/probe/q_field_inventory.py`
по захваченным архивам, окно 14.09.2026 17:00–19:00 UTC. Заполненность плавает
по времени суток в пределах 3–5 пунктов.

### VehiclePositions

| Поле | Заполнено |
|---|---:|
| `trip.route_id`, `direction_id`, `start_date`, `start_time` | 100% |
| `trip.trip_id` | **отсутствует** |
| `vehicle.id` | 100% |
| `position.latitude`, `longitude`, `bearing`, `speed` | 100% |
| `timestamp` | 100% |
| `current_status`, `stop_id` | 99.3% |
| `current_stop_sequence` | **0%** |

### TripUpdates

| Поле | Заполнено |
|---|---:|
| `trip.route_id`, `direction_id`, `start_date`, `start_time` | 100% |
| `trip.trip_id`, `vehicle.id` | **отсутствуют** |
| `timestamp` | 100% |
| `stop_time_update.stop_id`, `schedule_relationship` | 100% |
| `stop_time_update.stop_sequence` | **0%** |
| `arrival.time`, `departure.time` | 77.8% |
| `arrival.uncertainty` | 43.1% |
| `arrival.delay` | **0%** |

### Следствия

`trip_id` и `stop_sequence` отсутствуют. Рейс опознаётся четвёркой
`route_id + direction_id + start_date + start_time` — это рекомендация
[документации HSL](https://hsldevcom.github.io/gtfs_rt/), а не наш вывод.

`arrival.delay` пуст. Отклонение от расписания считается из GTFS static.

Не используются: `odometer`, `occupancy_status`, `departure.uncertainty`.

## 2. Периоды и объём

Замер 14.09.2026, окно 3.5 часа, 1113 снимков позиций.

| | Значение |
|---|---|
| Период обновления машины (дельта `vehicle.timestamp`) | медиана **10 с**, p90 11 |
| Доля дубликатов при дедупе по `(vehicle_id, ts)` | **3.7%** |
| Доля обновлений, где время изменилось, а координаты нет | **16.2%** |
| Уникальных рапортов | 962 тыс. за 3.5 ч → **198 млн/мес** |
| Размер записи позиции | **121 байт** protobuf, 42 после gzip |
| Размер записи прогноза | 29 байт protobuf, 9 после gzip |
| Сжатие gzip поверх protobuf | 2.9x (позиции), 3.2x (прогнозы) |

**Сжатие 3x — нижняя граница.** Это gzip поверх protobuf, где рядом лежат
разнородные поля одной записи. В колоночном хранилище значения одного типа
лежат подряд и сжимаются существенно лучше.

### Структура фида прогнозов

Одна запись = **рейс целиком**, включая уже пройденные остановки:

```
~1200 рейсов в снимке × ~31 запись = 37.6 тыс. записей
из них ~17 пройденных (факты) и ~14 будущих (прогнозы)
```

HSL пересылает рейс целиком каждые 15 секунд, включая прибытия двухчасовой
давности. При хранении «состояния на каждый момент» это **217 млн строк в
сутки**.

## 3. Факт прибытия

### Семантика

У HSL `arrival.uncertainty = 0` означает, что остановка пройдена, то есть это
**фактическое время, а не прогноз**. Подтверждено дважды:

- измерением: 14 720 записей с нулём, **все до единой в прошлом**, в будущем ноль;
- [документацией HSL](https://hsldevcom.github.io/gtfs_rt/): *«uncertainty is set
  to 0 for stops which the vehicle has passed»*.

У других агентств то же поле используется по прямому назначению — оценка
погрешности прогноза в секундах. Семантика фида проверяется отдельно для
каждого источника.

### Стабильность факта

141 386 фактов, окно 3.5 часа:

| | Значение |
|---|---|
| Не менялись после публикации | 95.2% |
| Изменились | **4.8%** |
| Направление правки | 99.6% вперёд (23 случая назад не объяснены) |
| Величина | медиана **+10 с**, p90 +24 |
| Когда | медиана 30 с после первой публикации, p90 60 с |
| Сколько раз | **ровно один**, второго исправления не бывает |

Доля правок растёт с временем жизни факта в фиде: 2% у недолгих, 10% у
наблюдавшихся больше сотни раз. Механизм неизвестен; проверено, что это не
коллизия ключа — рейсов с повторяющейся остановкой **ноль** из 141 386.

**Операционное правило: брать устоявшееся значение, не первое.** Ждать 60–120 с.
Вклад правок в метрику при этом: `0.05 × 10 с = 0.5 секунды` — пренебрежимо,
но правило бесплатное.

### Перекрёстная проверка двумя системами

Факт из фида прогнозов против `current_status = STOPPED_AT` из фида позиций,
71 422 пары. Источники независимы: позиции идут из бортовой телеметрии HFP,
прогнозы и факты — из операционной системы PubTrans.

```
STOPPED_AT минус факт:  медиана +4 с, p10 +0, p75 +7, p90 +9
|расхождение|:          медиана 4 с, p90 9 с
до 5 с — 60%,  до 15 с — 97%,  до 30 с — 99%
```

**Это и есть разрешающая способность метрики.** Вместе с величиной правок (~10 с)
даёт согласованную границу: **превосходство меньше 10 секунд заявлять нельзя.**

## 4. Точность официального прогноза HSL — предварительная оценка

**Окно 3.5 часа одного дня.** Порядок величины, не результат: для утверждения
о точности нужна история за месяцы и разбивка по часам, дням и маршрутам.

Корзины по времени до **фактического** прибытия,
допуски по методике [TransitApp/ETA-Accuracy-Benchmark](https://github.com/TransitApp/ETA-Accuracy-Benchmark).

| Корзина | MAE | p90 | В допуске | Пришёл раньше обещанного |
|---|---:|---:|---:|---:|
| 0–3 мин | **34 с** | 71 с | 93.9% | 15% |
| 3–6 мин | **52 с** | 103 с | 96.9% | 16% |
| 6–10 мин | **66 с** | 133 с | 96.6% | 16% |
| 10–15 мин | **81 с** | 165 с | 97.6% | 16% |
| 15–30 мин | 105 с | 219 с | — | 16% |
| 30+ мин | 149 с | 323 с | — | 14% |

Итог по методике TransitApp: **96.2%**

Прочерки на дальних корзинах — сознательный отказ: опубликованная методика
кончается на пятнадцати минутах, а выдумывать свой порог там, где его никто не
устанавливал, мы не стали.

### Две метрики расходятся в направлении

MAE растёт с горизонтом (34 → 81 с), доля в допуске **тоже растёт**
(93.9% → 97.6%). Допуск расширяется быстрее, чем растёт ошибка.

По одной мере прогноз на дальнем горизонте хуже втрое, по другой — лучше.
Обе правы. **Опубликованная доля точности бессмысленна без приложенной
методики:** агентства публикуют собственные допуски, и они шире — те же данные
дали бы по ним ещё более высокий процент.

### Оговорка по взвешиванию

Числа `n` в исходном расчёте — наблюдения, а не независимые события: один факт
даёт десятки прогнозов, пока лежит в будущем. Фактов 141 775. MAE внутри
корзины взвешен по времени пребывания в ней, а не по числу прибытий.

Для строгого соответствия методике нужен **один прогноз на пару
«факт — корзина»**. **Не пересчитано.**

## 5. Поведение прогноза

| | Значение |
|---|---|
| Горизонт: до прибытия | медиана 12 мин, p90 34, макс 133 |
| Дрейф между соседними снимками | медиана **0**, p90 **0** |
| Изменений за жизнь пары | медиана 5, среднее **6.8**, p90 16, макс 73 |
| Пар, не менявшихся ни разу | 11.4% |
| Пар с 10+ изменениями | 26.5% |

Противоречия между строками 3 и 4 нет: между двумя соседними снимками прогноз
почти всегда стоит, но за жизнь пары в 62 наблюдения набегает 5–7 правок.

**HSL выпускает прогноз и держит его.** Обгонять устойчивую систему труднее,
чем дёргающуюся: нет шума, который можно убрать сглаживанием.

## 8. Надёжность приёма

Захват 16–17.09.2026: **33 993 опроса, 2479 ошибок — 7.3%.** Все четыре фида
падают одновременно, то есть рвётся канал на стороне приёмника, а не у агентства.

Дневные часы 12–19 покрыты на 11–59%, ночные на 95–100%. Это не свойство фида,
а свойство домашнего интернета и ноутбука.

**Практическое следствие:** требование «мерить распределение потерь по времени,
а не только их долю» — не теоретическое. Потери здесь распределены крайне
неравномерно и приходятся на дневные часы, то есть на самые нагруженные.
Без нормировки по покрытию суточный профиль был бы искажён.

## 9. Что не измерено

- **Строгое взвешивание точности** — один прогноз на пару «факт — корзина».
- **69 рейсов (1.3%)**, присутствующих в фиде позиций и отсутствующих в фиде
  прогнозов. Гипотеза «пропуски захвата» проверена и опровергнута.
- **23 правки факта назад** из 5350.
- **Механизм правок факта.** Прогнозы HSL считает PubTrans ROI — коммерческая
  система, её кода нет. Открыт только пайплайн публикации HSL.

## Ограничение, которое нельзя снять

Мы измеряем не отклонение от реальности, а **отклонение от заявленного
эталона** — устоявшегося факта из фида HSL. Реальность недоступна никому.

Нельзя исключить, что факт и прогноз выведены внутри PubTrans общей логикой, и
тогда измеренная ошибка занижена. Снаружи это не проверяется. Имеющаяся
граница — расхождение в 4 секунды с независимой бортовой телеметрией.
