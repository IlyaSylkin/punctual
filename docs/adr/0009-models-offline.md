# ADR-009. Модели считаются офлайн, в резолвере

**Статус:** принято, 19.09.2026

## Контекст

Метрика оценивает прогноз в четырёх–шести точках на прибытие (границы корзин).
Живой расчёт моделей потребовал бы непрерывной работы и хранения всех прогнозов
всех моделей.

Отраслевая практика различает офлайн-путь (оценка, обучение) и онлайн-путь
(выдача), и требует **point-in-time correctness**: прогноз на момент T считается
только по данным, существовавшим до T. Нарушение — look-ahead bias, обесценивает
результат.

## Решение

Фаза 1: только офлайн-путь. Резолвер считает модели в момент разрешения
прибытия, из **датированного артефакта**.

Правило: прогноз на момент T использует артефакт, построенный на данных строго
до суток, содержащих T.

Артефакты: `segment_profiles` (v0) и `bias_table` (v1), оба строятся раз в сутки.
В `bias_table` применяется **иерархический откат**: берётся самая точная ячейка
с `n ≥ порога`, иначе поднимаемся — маршрут без часа, маршрут целиком, город.
Уровень записывается в строку.

## Альтернативы

**Живой scorer как потребитель Kafka** — корректен по построению (будущего не
существует), но избыточен для метрики. Понадобится в фазе 2 для демо и в фазе 4
для собственного фида.

**Расчёт без датированных артефактов** — отвергнуто: заглядывание в будущее
даёт завышенный результат, особенно для v1, которая обучается на тех же
измерениях, на которых проверяется.

## Проверка

Когда появится онлайн-путь, обязателен тест на расхождение: взять момент из
прошлого, посчитать прогноз офлайн-путём, сравнить с записанным онлайн-путём
тогда же. **Расхождение должно быть нулевым.**

## Следствия

Suточный цикл обновления артефактов оправдан дважды: воспроизводимостью
результата и запретом заглядывания. Одно решение закрывает две задачи.

Разреженность вынуждает огрублять ключи: в `segment_profiles` вместо 24 часов
используются шесть полос времени, иначе на ячейку приходится 7 наблюдений
в неделю вместо 28.
