# ADR-013. Миграции схемы — golang-migrate, обе базы

**Статус:** принято, 07.10.2026

## Контекст

Схема будет меняться всю жизнь проекта: добавится колонка, изменится TTL,
появится индекс. При этом пересоздать данные нельзя — фид прошлое не отдаёт
(О4), а схема обязана совпадать на ноутбуке, в CI и на сервере.

Нужен механизм, который применяет изменения по порядку, помнит применённое и на
повторный запуск не делает ничего.

Баз две: ClickHouse сейчас, Postgres для GTFS static в задаче #16.

## Решение

`golang-migrate`, запускается контейнером `migrate/migrate`, миграции лежат
файлами SQL:

```
migrations/clickhouse/NNNN_название.up.sql
migrations/clickhouse/NNNN_название.down.sql
migrations/postgres/…
```

Один инструмент на обе базы: одна конвенция, одна таблица состояния, один
способ запуска. Ставить на машину нечего — всё в образе.

## Альтернативы

**Alembic** — отвергнут для ClickHouse: построен на SQLAlchemy, поддержка
ClickHouse сторонняя и неполная. Для Postgres подошёл бы, но тогда в проекте
два механизма миграций с разными конвенциями.

**Свой запускатель на Python** — около полусотни строк, без новых зависимостей.
Отвергнут: стандартное решение предпочтительнее самодельного там, где оно есть,
и у готового уже решены частичный отказ и одновременный запуск.

**dbmate** — равноценен по возможностям, отвергнут по распространённости.

## Проверка

Применение должно оставаться повторяемым и на пустой базе, и на существующей.
Проверяется в CI: ClickHouse поднимается с нуля, миграции применяются, тесты
сверяют схему с `data-model.md`.

Если при переходе к Postgres окажется, что `golang-migrate` не покрывает нужды
миграций данных, а не только схемы, решение пересматривается.

## Следствия

У ClickHouse нет транзакционного DDL: упавшая миграция оставляет частичное
состояние и помечается `dirty`. Отсюда правило — **одна миграция меняет один
объект**, чтобы откат сводился к `DROP`.

Миграции не применяются автоматически при мерже. Выкатка — отдельный шаг,
появится в вехе 2.
