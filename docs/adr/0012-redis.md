# ADR-012. Redis: горячее состояние и счётчики

**Статус:** принято, 19.09.2026

## Контекст

Демо требует скользящих счётчиков и рассылки разрешённых прогнозов подписчикам.
Позиции машин перезаписываются 140 раз в секунду круглосуточно и живут 11 секунд.

## Решение

Redis хранит:

| Ключ | Тип | Зачем |
|---|---|---|
| `pos:hsl:<машина>` | хэш, TTL 5 мин | текущие позиции |
| `wins:hsl:<модель>:<минута>` | счётчик, TTL 20 мин | скользящее окно 15 минут |
| `recent:hsl` | список до 50 | лента при открытии страницы |
| канал `resolutions:hsl` | pub/sub | **ничего не хранит** |

Меньше мегабайта суммарно.

## Альтернативы

**Postgres для горячего состояния** — отвергнуто: 140 обновлений в секунду
круглосуточно создают ~12 млн мёртвых версий строк в сутки (MVCC) и постоянную
работу автовакуума. Это плата за долговечность, которая не нужна: позиция живёт
11 секунд.

**Гео-набор `GEOADD`/`GEOSEARCH`** — **отвергнуто**. Требование «показать машины
рядом с точкой» на нашем масштабе не существует: 1306 машин это 78 КБ JSON, весь
город проще отдать браузеру целиком и фильтровать локально. Вернуть, если парк
вырастет на порядок или одновременных зрителей станет больше сотни.

**Счётчик простым `INCR` с TTL** — отвергнуто: даёт окно «с момента создания
ключа», а не скользящее. Нужны минутные корзины с суммированием пятнадцати
последних.

## Проверка

**Redis должен быть полностью восстановим из ClickHouse и фидов.** Если
что-то существует только в нём — это ошибка проектирования. Проверяется просто:
очистить Redis на работающей системе; потеряться должны только секунды удобства.

## Следствия

Redis не нужен для метрики — только для витрины. В фазе 1 не требуется.

Pub/sub ничего не хранит: не было подписчика в момент отправки — сообщение
исчезло. Приемлемо, потому что через секунду будет следующее; данные, которые
терять нельзя, идут через Kafka.
