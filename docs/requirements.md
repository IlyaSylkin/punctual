# Требования

Выход стадии требований. Границы проекта заданы уставом (`CHARTER.md`),
здесь — что система делает внутри этих границ и каким свойствам отвечает.

Редакция от 19.09.2026.

Приоритеты: **M** — без этого проекта нет, **S** — важно, запуск переживёт,
**C** — при наличии времени и выполнении условия.

## Нефункциональные требования

### Корректность измерения

| | Требование | |
|---|---|---|
| Н1 | Различия меньше **10 с** не интерпретируются: это разрешающая способность, заданная расхождением независимых определений прибытия | M |
| Н2 | Потери приёма **менее 2%** за календарный месяц | M |
| Н3 | Потери **распределены равномерно**: доля потерь в любом часе суток не превышает удвоенной средней | M |
| Н4 | Результат пересчитывается из сырья одной командой | M |

Н3 важнее Н2: равномерные 5% оставляют метрику несмещённой, а потеря каждого
часа пик смещает её, даже если общая доля мала.

### Производительность и ресурсы

| | Требование | |
|---|---|---|
| Н5 | Лаг приёма (`ingested_at − ts`) менее 30 с в 99% времени | M |
| Н6 | Страница результатов отвечает менее чем за 1 с | S |
| Н7 | История за 4 месяца помещается в 100 ГБ | M |
| Н8 | Вся система работает на одном VPS 8–16 ГБ | M |

### Наблюдаемость и эксплуатация

## Ограничения

Не обсуждаются, заданы снаружи.

| | Ограничение | Следствие |
|---|---|---|
| О1 | Один VPS, бюджет около 2000 ₽/мес | исключает k8s, кластеры, реплики |
| О2 | Только открытые данные HSL; лицензия требует указания источника | публикуемые данные производные, атрибуция обязательна |
| О3 | Один разработчик, 2–3 часа в день | при нехватке времени режется скоуп, не срок |
| О4 | **Фид эфемерен**: историю за прошлое получить нельзя | приём не может прерываться; пропуск невосстановим |
| О5 | Точность ограничена снизу ~10 с | свойство данных, а не наше решение |
| О6 | Прогнозы HSL считает закрытая система PubTrans | нельзя проверить, не выведены ли прогноз и факт общей логикой |
