# Как вносить изменения

## Окружение

```bash
docker compose up -d          # поднять зависимости
pip install -e ".[dev]"
pre-commit install            # ruff, mypy, проверка формата коммита
pytest                        # тесты идут против настоящих БД в контейнерах
```

## Ветки

```
feat/<что>      fix/<что>      perf/<что>     refactor/<что>
test/<что>      docs/<что>     build/<что>    ci/<что>      chore/<что>
```

В `main` не коммитить. Ветка → PR → squash-мерж.

## Коммиты

Conventional Commits:

```
<тип>(<область>): <что сделано, повелительное наклонение>

<почему; что рассматривалось и отвергнуто; что ломается>

Refs #12
```

**Типы:** `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`.

**Области:** `ingestor`, `sink`, `resolver`, `api`, `airflow`, `ch`, `pg`,
`redis`, `kafka`, `infra`, `docs`, `probe`.

**Заголовок:** до 50 символов, строчная после двоеточия, без точки в конце,
продолжает фразу «Этот коммит, если применить, …».

**Тело** отвечает на «почему», а не на «как» — как видно из диффа.

**Один коммит — одно логическое изменение.** На каждом коммите проект
собирается и тесты проходят. Форматирование идёт отдельным коммитом от логики:
иначе содержательная строка теряется в диффе на двести строк.

## Pull request

- один PR — один тикет;
- до 400 строк изменений, дальше качество ревью падает — разбивать;
- в описании: что, почему, как проверял;
- ревью на следующее утро, не сразу;
- мерж squash, `main` остаётся линейным.

## Проверки

Настроены в `.pre-commit-config.yaml` и в CI, выполняются машиной:

| Что | Чем |
|---|---|
| линтер и форматтер | `ruff` |
| типы | `mypy` |
| формат сообщения коммита | хук `commit-msg` |
| большие файлы, приватные ключи, конфликтные маркеры | `pre-commit-hooks` |
| тесты | `pytest` в CI |

Красный CI блокирует мерж, включая собственный.

## Версии и CHANGELOG

`CHANGELOG.md` генерируется из истории коммитов, версия бампается по типам:
`feat` — минорная, `fix` — патч, `BREAKING CHANGE` в теле — мажорная.

## Definition of Ready

Задачу можно брать в работу, если:

- понятно, из какого требования она следует (`docs/requirements.md`);
- записаны критерии приёмки — что должно быть верно, чтобы задача считалась
  выполненной;
- нет неотвеченных вопросов, блокирующих начало;
- задача помещается в один PR до 400 строк; иначе разбить.

## Definition of Done

Задача сделана, если выполнено всё:

- [ ] критерии приёмки выполнены и проверены;
- [ ] код покрыт тестами; тесты, затрагивающие БД, идут против настоящих БД
      в контейнерах, а не против моков;
- [ ] `ruff` и `mypy` проходят;
- [ ] решения, у которых была альтернатива, записаны в `docs/adr/`;
- [ ] изменение затронуло контракт или схему — соответствующий документ обновлён;
- [ ] PR прошёл ревью (на следующее утро, не сразу) и смержен squash;
- [ ] изменение выкачено и работает на сервере;
- [ ] если добавлен компонент — у него есть метрика и он виден в мониторинге.

Последний пункт неочевиден, но без него компонент падает молча, и об этом
узнают из кривых цифр через неделю.
