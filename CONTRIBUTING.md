# Как вносить изменения

Главная мысль: в нормальной команде история коммитов — это **документация
изменений**, которую читают. Читают при разборе инцидента («когда сломалось и
что тогда меняли»), при ревью, при подготовке релиза. Поэтому у неё есть формат.

---

## 1. Формат сообщения: Conventional Commits

```
<тип>(<область>): <что сделано в повелительном наклонении>

<почему это сделано, что рассматривал и отверг, что ломается>

Refs #12
```

Пример:

```
feat(ingestor): вычислять период опроса из header.timestamp фида

Фиксированный интервал в 10 с давал 5 дубликатов на каждое событие OVapi
(период фида 60 с) и при этом отставал от HSL (11 с). Теперь период
берётся из наблюдаемой дельты header.timestamp, с потолком в 60 с.

Альтернатива — конфиг с интервалом на фид — отвергнута: агентства меняют
период без предупреждения, конфиг протухнет молча.

Refs #12
```

### Типы
| Тип | Когда |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление бага |
| `perf` | ускорение без смены поведения |
| `refactor` | изменение кода без смены поведения и без ускорения |
| `test` | только тесты |
| `docs` | только документация |
| `build` | зависимости, Dockerfile, сборка |
| `ci` | пайплайн |
| `chore` | остальное: конфиги, скрипты, рутина |

### Области в этом проекте
`ingestor`, `sink`, `hot-writer`, `api`, `airflow`, `ch`, `pg`, `redis`,
`kafka`, `infra`, `docs`

### Правила заголовка
- повелительное наклонение: «добавить», не «добавил» и не «добавление»
- до 50 символов, без точки в конце
- строчная буква после двоеточия
- заголовок должен продолжать фразу «Этот коммит, если применить, ...»

### Тело
Отвечает на **почему**, а не на **как**. Как — видно из диффа. Почему —
не видно никогда, и через три месяца ты сам не вспомнишь.

Хорошее тело содержит отвергнутую альтернативу. Это то, что превращает
историю в документацию решений.

## 2. Атомарность — самое сложное и самое ценное

Один коммит = одно логическое изменение. Проверка: **на этом коммите проект
собирается и тесты проходят**, и его можно откатить, не задев ничего другого.

Из этого следует правило, которое чаще всего нарушают:

> Изменения форматирования идут **отдельным** коммитом от изменений логики.

Если переформатировать файл и заодно поправить логику, дифф на 200 строк, и
ревьюер физически не найдёт в нём одну содержательную строчку. В команде за
такое разворачивают PR не глядя.

Практически: `git add -p` вместо `git add .`. Разбирать изменения по кускам —
это навык, он ставится за неделю и остаётся навсегда.

## 3. Ветки

```
feat/ingestor-adaptive-poll
fix/ch-batch-size-overflow
docs/adr-kafka
chore/bump-deps
```

Тип совпадает с типом коммита. Никаких `new`, `test2`, `my-branch`.

**В `main` не коммитить никогда.** Даже опечатку в README. Ветка → PR → мерж.

---

## 4. Pull request

- **Один PR = один тикет.** Не «заодно поправил ещё вот тут».
- **До 400 строк изменений.** Это не вкусовщина: после этого порога качество
  ревью обваливается, человек перестаёт видеть детали. Больше — разбивай.
- Заголовок PR по тому же формату, что коммит.
- В описании: что, почему, как проверял, скриншот или вывод команды.
- **Ревью на следующее утро**, не сразу. Свой код через двенадцать часов
  читается чужими глазами — это работает, проверено на всех.
- Мержим **squash**: main остаётся линейным, один коммит в main = одна
  законченная функциональность. Подробные коммиты сохраняются внутри PR.

---

## 5. Что выдаёт джуна в истории

- `update`, `fix`, `wip`, `изменения`, `.`
- «Initial implementation» на 2000 строк
- Закоммиченные `.env`, ключи, `__pycache__`, `.venv`, дампы данных
- Форматирование вперемешку с логикой
- Коммиты в main
- Пять коммитов подряд `fix ci`, `fix ci 2`, `fix ci really` — их надо было
  сложить в один перед мержем

## 6. Не полагаться на дисциплину — включить проверки

Это и есть главное отличие «как в проде»: правила соблюдаются машиной, а не
силой воли.

**`pre-commit`** — стандарт в Python. В `.pre-commit-config.yaml`:
- `ruff` — линтер и форматтер
- `mypy` — типы
- проверка на большие файлы, приватные ключи, конфликтные маркеры, хвостовые пробелы
- `commitizen` или хук `commit-msg` — проверяет формат сообщения

**CI на PR** — то же самое плюс тесты. Красный CI блокирует мерж, включая твой
собственный. Это настраивается в защите ветки `main` на GitHub, и это надо
включить сразу, а не потом.

Настраивается всё в фазе 1, в первый же день, вместе с каркасом. Позже
поставить — значит сначала накопить сотню коммитов, которые не соответствуют
собственной конвенции.

---

## 7. CHANGELOG и версии

Раз формат машиночитаемый, `CHANGELOG.md` генерируется из истории, а версия
бампается по типам: `feat` → минорная, `fix` → патч, `BREAKING CHANGE` в теле
→ мажорная. Инструмент — `commitizen` или `git-cliff`.

Это не для красоты: релиз с внятным списком изменений — то, по чему при
инциденте за минуту находят, что именно поехало.
